## 1. 文档目的

本方案用于指导乐秀平台下一轮产品、交互、视觉、可靠性和验收优化。它是评审稿，不代表已经修改代码、启动服务、修改生产数据或发布服务器。

用户确认本方案后，先补齐对应框架文档，再在 v1.14.7 基线上进行隔离本地开发和验证。未经用户本机验收并明确允许发布，不打包、不上传、不重启生产服务。

## 2. 产品定位与目标

乐秀平台是单店、50 人以内使用的内部管理平台，核心价值不是扩展成大型管理套件，而是让门店人员在电脑和手机上可靠完成以下工作：

1. 保存企业证照、员工健康证和消防照片档案，并持续看到有效期与缺失项。
2. 登记固定资产领用、归还，保持资产去向可查。
3. 完成仓库采购入库、消耗出库和盘点，保持库存数量与流水一致。
4. 让普通员工可以提交资料、附件、资产和仓库物品，管理员集中审核关键变更。
5. 让管理员维护公开酒水单，并确保客人侧只看到允许公开的最少字段。
6. 保证资料、附件、密钥、数据库和备份在故障时可追溯、可恢复。

本轮优化目标是：

- 员工现场操作少思考、少重复填写、少走错路径。
- 管理员一打开工作台就能优先处理到期、库存风险和待审核事项。
- 桌面与手机使用同一套业务规则，差异只体现在布局和操作顺序。
- 关键状态、错误、空态、加载、权限和审核结果都能被清楚理解。
- 任何改动都能通过隔离测试、双端验证、独立复测和用户验收追溯。

## 3. 当前基线与约束

### 3.1 已有能力

- 技术栈：Flask + SQLite + 原生 JavaScript/CSS。
- 业务模块：登录、工作台、企业证照、员工健康证、固定资产、仓库、审核中心、消防档案、酒水单、系统设置和备份。
- 视觉基线：黑金登录、首页和导航；米白列表、详情、表单和审核业务页。
- 用户角色：`admin` 与 `staff` 两类系统角色。
- 普通员工：可查看和修改允许范围内的资料，可新增资产与仓库物品，可上传附件和仓库图片；需要审核的内容由管理员确认后生效。
- 管理员：负责审核、删除、账号、酒水单、台账下载和直接生效的维护操作。
- 生产数据：全部集中在 `data/`，本机测试数据不得覆盖或反向导入服务器。
- 发布闸门：本机开发与验证 → 用户本机验收 → 用户明确“可以发” → 打包 → 备份 → 上传 → 迁移 → 重启 → 线上核对。

### 3.2 当前未完成验证

以下内容不能因代码或隔离测试通过而直接视为完成：

- iOS Safari、Android Chrome、微信环境、真实摄像头和系统键盘。
- 读屏、键盘完整操作和全站无障碍一致性。
- 长期运行、容量、图片处理内存和 SQLite 并发基线。
- 自然备份累计第 4 套后两端只保留最近 3 套的真实证据。
- 与最新版本对应的 WorkBuddy 独立复测结论。

## 5. 设计原则

1. **任务优先**：首页优先展示需要处理的事项，不用装饰性统计替代行动入口。
2. **现有能力优先**：优化现有流程和理解成本，不借机增加多店、推送、出库审批、商品价格库、SKU、批次或新角色。
3. **同一规则、不同布局**：桌面适合集中查阅，手机适合现场登记；字段、权限和结果口径一致。
4. **状态可解释**：待审核、当前有效、已退回、已过期、15 天内到期、长期有效和待确认有效期均需清楚展示。
5. **后端为最终门槛**：前端隐藏入口不能代替后端权限、来源、入参和附件校验。
6. **证据优先**：每项改动都要有命令、页面、账号、视口、数据数量或复测结论等可追溯证据。

## 6. 目标信息架构

### 6.1 桌面端

保留左侧模块导航和顶部用户区，按工作域理解模块：

- 工作台
- 档案与合规：企业证照、员工健康证、消防档案
- 资产与物资：固定资产、仓库管理
- 管理工具：审核中心、酒水单、系统设置

审核中心、酒水单和系统设置继续按管理员权限显示。消防档案作为独立路由保留业务结构，但统一返回工作台、当前用户提示和审核入口表现。

### 6.2 手机端

保留“工作台 / 应用 / 我的”底部导航：

- 工作台：提醒、待办和最常用任务。
- 应用：按“档案与合规 / 资产与物资 / 管理工具”分组进入现有模块。
- 我的：修改密码、退出登录和管理员工具。

进入子页后必须能知道当前模块、返回上级，并在切换模块时处理滚动位置和焦点。普通模块切换回到页面顶部；从提醒进入详情后返回，保留来源位置。

## 7. 工作台设计

v1.14.7 已采用“只展示有实际内容的提醒”策略，本方案继续采用该策略，不直接恢复旧版被隐藏的统计卡和常用模块卡。

工作台按以下顺序组织：

1. 当前门店状态摘要。
2. 管理员待审核事项（有内容时突出显示）。
3. 证照和健康证到期提醒。
4. 仓库库存和有效期预警。
5. 常用模块入口或“进入应用”入口。

没有提醒时显示清晰的正常状态和可执行入口；不显示空白卡片。应用入口需要足够明显，避免用户因为提醒优先而找不到模块。

## 8. 核心交互规范

### 8.1 页面状态

所有列表和关键区域统一具备：加载中、加载失败、空数据、正常数据和可重试状态。失败提示必须告诉用户下一步，不只显示短暂 Toast。

搜索输入采用轻量防抖，并使用请求标记只接受最后一次结果，避免旧关键词请求覆盖新结果。

### 8.2 返回与焦点

- 子页返回显示明确的上级名称，不统一写成“返回仪表盘”。
- 视图切换后更新页面标题和可访问的路由播报。
- 新页面将焦点移到页面标题或当前模块标题。
- 弹窗打开时锁定背景滚动，关闭后恢复原滚动位置和触发按钮焦点。

### 8.3 表单、上传和审核

- 手机表单保持主要信息 → 补充信息 → 确认的顺序。
- 有未保存内容时，关闭、返回、导航和退出登录都先提示。
- 保存失败或附件失败时保留可重试的输入和文件选择。
- 审核页面同时展示提交内容、原内容、申请人、状态和退回原因。
- 现行规则优先于旧原型：资料删除由管理员后端控制，不恢复旧文档中的“手输全名”要求；员工新增资产和仓库物品按当前规则进入审核。
- 本方案暂按现行 `AGENTS.md` 口径处理健康证编号、发证机构和到期日；如需调整必填性，必须在开发前单独裁定。

### 8.4 图片、附件和打印

- 证照、仓库和消防照片保持完整比例显示。
- 非图片附件使用统一封面，并提供明确的原文件入口。
- 图片大图、消防照片和酒水放大图支持键盘 Enter/Space 打开，关闭后恢复焦点。
- 消防打印只包含已生效照片，保持固定目录顺序和 A4 一图一页。

## 9. UI 与设计系统

### 9.1 视觉令牌

- 登录、工作台、导航背景：黑金基调。
- 业务页背景：米白基调。
- 主要操作：金色或深金色按钮。
- 删除、错误、退回：独立红色语义，不与成功状态混用。
- 状态不能只依赖颜色，必须同时有文字。

### 9.2 组件范围

建立现有原生页面可复用的组件约定：按钮、输入框、下拉框、表格、资料卡、状态标签、附件卡、弹窗、提示、加载状态、空状态、错误重试区和底部导航。

每个组件至少定义默认、悬停、焦点、禁用、加载、错误、待审核和权限不可用状态。

### 9.3 响应式验收尺寸

- 桌面：1366px、1440px，并补查 1024px。
- 手机：320px、390px、430px。
- 触控区域不小于 44px。
- 320px 下证照卡和长文件名不得逐字挤压或溢出。

## 10. 技术实施边界

本轮不更换 Flask、SQLite、原生 JavaScript/CSS，不引入新的前端框架或测试框架。

重点实施边界：

- 优先调整 `templates/`、`static/app.js`、`static/fire.js`、`static/style.css` 的体验层逻辑。
- 后端只在确有业务闭环、权限或一致性需要时调整，保持现有接口和数据结构兼容。
- 所有新增字段或表必须先写框架文档，登记迁移和双备份要求。
- 所有写接口继续使用统一入参校验、来源校验、重复提交保护和事务回滚。
- 不修改 `data/app.db`、`data/uploads/`，不把本机测试数据带入发布包。

## 11. 安全、数据与可靠性验收

必须覆盖以下检查：

1. 管理员和普通员工看到的入口、数据和操作边界正确。
2. 缺少 `X-Requested-With` 或本站 `Origin` 的写请求仍返回 403。
3. 附件上传失败、损坏图片、零字节文件和超限文件均能回滚并清理孤立文件。
4. 数据库结构变更前同时完成 SQLite 一致性快照和完整 `data/` 备份。
5. 生产公开酒水接口不返回后台字段，公开图片优先使用压缩图。
6. 备份、恢复、回退和版本核对均有实际证据；未验证内容单独标注。
